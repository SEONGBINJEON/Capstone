# 03. 리더→팔로워 추종 루프 설계

파일: `teleoperation/sim_teleop/teleop.py` 의 `run()`. 아래 순서로 읽으면 됩니다.

## 1) 준비 검사 (preflight)

토크를 켜기 전에 4번 샘플링해서 확인하는 것:
- 모든 모터 응답, 하드웨어 오류 없음, 온도·전압 정상 (`health`)
- 리더 토크가 전부 OFF (사람 입력 장치)
- 팔로워가 준비 중에 움직이지 않음 (4 tick 이내)
- 각 팔로워의 현재 위치가 허용 범위(모터 EEPROM 제한 ∩ 그리퍼 개폐 범위) 안
- 리더 기준 목표까지의 "시작 정렬 이동량" 계산. 150° 넘으면 시작 거부(사람이 리더를 팔로워와 비슷한 자세로 놓게 함)

`--dry-run`은 여기까지만 하고 끝납니다. 새 설정을 시험할 때 항상 이걸 먼저 돌립니다.

## 2) 토크 ON (arm)

순서가 중요합니다.
1. watchdog 255(래치된 오류)면 0으로 지우기
2. 토크 OFF인 모터는 느린 프로파일 + **현재 위치를 목표로** 먼저 쓴다 → 토크가 켜질 때 튀지 않음
3. watchdog 15 설정
4. 다시 읽어 위치가 8 tick 이상 안 움직였는지 확인
5. 토크 ON, 그리고 정말 켜졌는지 확인

## 3) 상태 기계

```
aligning ──(모든 관절 5° 이내로 3주기 연속)──► following
   ▲                                              │
   │                       추종 오차 20° 초과 or 걸림 감지
   │                                              ▼
   └──────(초기 정렬만 저속) ...            blocked(자세 유지)
                                                  │ 1초 경과(오차형) / 리더가 되돌아옴(걸림형)
                                                  ▼
                                              following (즉시 180°/s)
```

- **aligning**: 시작 직후만. 15°/s로 천천히 리더 자세로 맞춘다. 팔로워가 어디 있든 안전하게 합류.
- **following**: 180°/s 제한 추종.
- **blocked**: 현재 위치를 목표로 다시 써서 그 자리에 고정. 토크는 유지(중력 부하가 있는 팔을 떨어뜨리지 않기 위해).

이번에 고친 버그: blocked → aligning으로 돌아가게 했더니, 끝까지 못 가는 관절이 하나 있으면 정렬이 끝나지 않아 15°/s에 갇혔습니다. 재개는 following으로 바로 가되 `commanded`를 현재 위치에 앵커링해 급가속을 막습니다.

## 4) 한 주기(50 ms) 안에서 하는 일

1. `rig.sample()`로 전 모터 읽기. 주기가 150 ms를 넘으면 정지.
2. `health`, 팔로워 토크·watchdog 상태 변화 검사.
3. 리더 한 주기 변화가 30° 넘으면 정지(통신 오류나 감김 의심).
4. 목표 계산 `joint_target()`: 관절은 기준점+편차×방향, 그리퍼는 닫힘~열림 사이 비율로 매핑.
5. 관절별로:
   - 추종 오차 = 모터 내부 궤적 − 실제 위치. 20° 넘으면 blocked.
   - **걸림 감지**: 목표와 5° 이상 차이가 나는데 위치가 0.5° 이내로 1.4 s 이상 안 움직임 → blocked(걸림형). 밀고 있던 방향을 기억해 리더가 그 반대로 돌아올 때만 재개.
   - 슬루 제한: `goal = anchor + clamp(target − anchor, ±speed·dt)`. 목표가 방향을 바꾸면 anchor를 현재 위치로 리셋해 반대편으로 튀는 것을 막음.
   - 선행 제한: goal이 실제 위치보다 10° 이상 앞서지 못함. 손이 빨리 움직여도 모터 궤적이 길게 밀리지 않음.
6. 바뀐 목표만 `stream_goals()`로 sync write(속도 프로파일 포함).
7. UDP로 팔로워 각도 발행, 20주기마다 콘솔 요약 출력.
8. 남은 시간만큼 sleep(정확히 50 ms 주기 유지).

## 5) 종료 처리 (finally)

Ctrl+C든 예외든 반드시 지나는 곳: 현재 위치를 목표로 다시 쓰고(자세 유지), watchdog을 0으로 되돌립니다. 토크는 끄지 않습니다. 토크 해제는 사람이 팔을 받친 뒤 `--release`(5초 카운트다운)로만.

## 왜 이런 숫자인가

| 값 | 이유 |
|---|---|
| 주기 50 ms | Sync read 2포트 + write에 약 10~15 ms. watchdog 300 ms의 1/6이라 한두 번 놓쳐도 안전 |
| 정렬 15°/s | 사람이 손으로 막을 수 있는 속도 |
| 추종 180°/s | 손 동작을 자연스럽게 따라오는 상한. XL430 무부하 최고속의 절반 정도 |
| 선행 10° | 20° 오차 허용과 함께, 목표가 앞서가도 오차 판정이 오탐되지 않는 조합. 이전 값(21°)은 12° 허용과 충돌해 오탐을 냈음 |
| 걸림 1.4 s / 5° | 과부하 래치(수 초)보다 먼저 멈추되, 느린 정렬 중 정상 지연을 오탐하지 않는 시간 |

## 보정(calibration)의 의미

- `leader_zero`, `follower_zero`: **같은 물리 자세**(여기서는 일자로 세운 자세)일 때 각각의 tick. 이 두 값이 다른 자세를 가리키면 팔이 어긋난 채 상대 움직임만 따라갑니다(`--match`로 시작했을 때 겪은 현상).
- `direction`: 같은 방향으로 돌릴 때 tick이 같은 부호로 변하면 +1. 모터 장착 방향이 반대면 −1.
- 그리퍼는 각도가 아니라 **개폐 비율**로 매핑합니다. 리더와 팔로워의 기구 비율이 달라도 닫힘↔열림이 대응되게.
- 시뮬 매핑(`sim.sign`, `view_sign`, `offset_deg`, `zero_ticks`)은 URDF 관절 방향과 실물 방향이 다를 때 화면만 뒤집는 값입니다. 로봇 제어에는 영향이 없습니다.

## 스스로 답해볼 문제

2. 팔로워가 장애물에 부딪혔을 때 코드가 그것을 어떻게 "알아채는가"? 두 가지 경로를 설명해 보라.
3. 토크 ON 순서에서 "현재 위치를 목표로 먼저 쓴다"를 빼면 어떤 일이 생기는가?
4. 이 구조에서 지연(latency)의 원인은 무엇이고 어떻게 줄일 수 있는가? (주기, 프로파일 시간, 선행 제한)
