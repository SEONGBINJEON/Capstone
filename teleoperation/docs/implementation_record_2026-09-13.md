# A/B 텔레오퍼레이션 구현 및 인계 기록

작성일: 2026-09-13, 한국 시간. 프로젝트 경로: `/home/jeonseongbin/Teleoperation`.

이 문서는 2026-09-12~13 작업의 최종 구현 상태를 정리합니다. 초기 시험 중간값은 `calibration_A.md` 등 기존 기록에 남기고, 현재 실행·설정은 이 문서와 `START_HERE.md`, `config/robot.json`을 기준으로 합니다.

**최종 종료 상태:** 아래 1~11절은 추종 구현과 당시 관측 기록입니다. 이후 사용자가 토크 OFF와 당일 작업 종료를 요청하여 활성 모터 18개 모두 토크 OFF를 확인하고 서비스도 종료했습니다. 마지막 변경 및 재시작 안내는 12절을 참고합니다.

## 1. 사용자가 정한 동작

- 리더 A 16~20 → 팔로워 A 11~15, 리더 B 26~30 → 팔로워 B 21~25.
- 관절 번호는 순서대로 1:1 대응합니다. 두 쌍의 마지막 모터가 그리퍼입니다.
- 링크 길이는 다르지만 전달 비율과 대응 축 방향이 같다는 사용자 확인에 따라 팔 관절 각도 배율 1, 방향 +1을 사용합니다.
- 리더를 편한 자세에 내려놓고 실행하면 팔로워가 현재 리더 자세로 천천히 맞춰진 뒤 빠르게 따라갑니다.
- B 그리퍼는 하드웨어 문제로 사용자가 보류했습니다. 25·30번은 읽기와 쓰기 모두 제외합니다.
- Isaac Sim 연동은 추후 작업입니다. 현재 실물 A/B 추종에 포함하지 않았습니다.

## 2. 정확한 실행 명령

```bash
cd /home/jeonseongbin/Teleoperation
.venv/bin/python run_teleop.py
```

바탕화면 등 어느 위치에서든 실행 가능한 명령:

```bash
/home/jeonseongbin/Teleoperation/.venv/bin/python /home/jeonseongbin/Teleoperation/run_teleop.py
```

실행기는 자체적으로 프로젝트 폴더로 이동합니다. 기존 서비스가 있으면 연결을 재사용하고, 없으면 배경 서비스를 시작합니다. 기본 선택은 A/B 동시입니다. 상태만 확인하려면 실행 명령 끝에 `--status`를 붙입니다.

자세 유지: `.venv/bin/python run_teleop.py --hold` 또는 실행 화면의 Ctrl+C. 토크를 해제하지 않습니다. A/B 선택과 장애물 수동 재개 명령은 `START_HERE.md`에 정리했습니다. 터미널 창을 닫는 동작을 정지 명령 대신 사용하지 않습니다.

## 4. 최종 보정값

팔 관절 목표는 `팔로워 기준 + 기준 대비 리더 변화 × direction × scale`로 계산하고 허용 위치 범위로 제한합니다. 회전 경계의 리더 변화는 한 회전 기준으로 처리합니다. 아래 값은 tick 단위이며, `4096 tick = 360°`입니다.

| 대응 | 리더 기준 | 팔로워 기준 | 방향 | 배율 |
|---|---:|---:|---:|---:|
| 16 → 11 | 4093 | 1060 | +1 | 1 |
| 17 → 12 | 2027.6222222222223 | 2334.222222222222 | +1 | 1 |
| 18 → 13 | 2076 | 1995 | +1 | 1 |
| 19 → 14 | 2060 | 2064 | +1 | 1 |
| 26 → 21 | 12 | 2048 | +1 | 1 |
| 27 → 22 | 2036 | 2052 | +1 | 1 |
| 28 → 23 | 2047 | 2042 | +1 | 1 |
| 29 → 24 | 2051 | 2061 | +1 | 1 |

A는 두 팔을 일자로 위로 세운 기준에서 시작했습니다. A 어깨는 사용자가 리더 링크 약 1° 아래, 팔로워 링크 약 10° 아래라고 관찰한 차이를 보정했고, 이후 사용자가 자세가 맞는다고 확인했습니다. 이는 해당 자세의 현장 확인이며 전 작업 공간 정밀도 측정을 의미하지 않습니다.

A 베이스 11번은 Homing Offset 0 → 1024, 작동 모드 3 → 4로 변경했습니다. 논리 기준은 1060이며 소프트웨어 범위 548~1572, 즉 기준 좌우 45°가 남아 있습니다. 기존 기록의 기준 36은 원점 변경 전 값입니다.

B는 두 팔을 일자로 위로 세우고 저장했습니다. 21번은 작동 모드 4, Homing Offset 0이며 원시 기준 4080을 논리 기준 2048로 대응시킵니다. 소프트웨어 범위는 1~4095입니다. 원시/논리 좌표 차이를 세션 동안 고정하여 뜻하지 않은 위치 점프를 새 원점으로 받아들이지 않습니다.

그리퍼 보정:

| 대응 | 리더 닫힘 / 열림 | 팔로워 닫힘 / 열림 | 상태 |
|---|---|---|---|
| 20 → 15 | 68 / 1533 | 916 / 2279 | 개폐 구간 비율로 대응, 활성 |
| 30 → 25 | 160 / 미보정 | 2086 / 미보정 | 하드웨어 문제로 비활성 |

### 선호 시작 자세와 영점의 차이

사용자가 마지막으로 선택한 편한 리더 자세는 `config/start_pose.json`에 따로 저장했습니다.

```text
A: 16=4103, 17=2348, 18=3177, 19=2922, 20=69
B: 26=-8,   27=2383, 28=3168, 29=2948
```

이 값으로 영점을 다시 잡지 않았습니다. 실행기는 이 파일의 고정 숫자로 팔로워를 보내는 대신 매 실행 당시의 실제 리더 위치를 읽습니다. 시작 정렬 중에도 최신 리더 위치를 사용합니다.

## 5. 반응 속도와 제어 방식

| 항목 | 현재 동작 |
|---|---|
| 제어 갱신 | 20 Hz, 약 50 ms 주기 |
| 첫 실행 정렬 | 최대 15°/s |
| 일반 추종 | A/B 각각 최대 180°/s |
| 반대 방향 복귀 또는 자세 일치로 자동 재개 | 즉시 일반 추종 속도 사용 |
| 명령으로 수동 재개 | 최대 15°/s 정렬 후 일반 추종 |
| 시작 도착 판단 | 목표 갱신 도착 + 실제 위치 5° 이내, 연속 3회 |
| 목표 처리 | 매 주기 최신 리더 값으로 교체, 이전 동작을 끝까지 수행하는 큐 없음 |
| 방향 반전 | 현재 위치 반대쪽 목표가 들어오면 이전 진행 목표를 취소 |
| 목표 선행 범위 | `max(8°, 속도 × 0.12초)`, 180°/s에서 21.6° |
| 목표 송신 | 바뀐 관절만 묶어서 송신, 프로파일 속도 전환 때 갱신 |

180°/s는 명령 속도의 상한이며 모든 모터가 모든 하중에서 그 속도를 내거나 특정 종단 지연을 보장한다는 의미는 아닙니다.

속도 기반 모터는 빠른 추종에서 Profile Acceleration=50을 사용합니다. 기존 5보다 가속을 높여 지연을 줄였습니다. 시간 기반 모터는 작은 목표에도 긴 이동 시간을 반복 설정하던 부분을 수정해 최소 한 제어 주기부터 이동 시간을 계산합니다. 각 모터의 Drive Mode에 따라 처리하므로 모두 같은 프로파일 숫자를 쓰지는 않습니다.

자동 재개 때 새 제어기가 기본 `aligning` 상태로 생성되어 15°/s로 느리게 따라가던 문제를 수정했습니다. `leader_retreated`와 `leader_pose_matched` 재개는 바로 `following`으로 전환하되 유지하던 목표에서 출발합니다. 주기별 목표 변화, 선행 범위, 가속 프로파일은 유지합니다.

## 6. 장애물 대기 및 재개

접촉 센서로 장애물을 식별하지 않습니다. 실제 위치가 모터 내부 이동 궤적과 12° 넘게 벌어지거나, 충분한 목표 오차가 있는데 약 1.4초 동안 거의 진행하지 못하면 `MotionBlocked`로 판단합니다.

1. 막힌 A 또는 B 쌍만 자세 유지로 바꿉니다. 같은 팔의 이미 안정적으로 지지 중인 관절은 기존 유지 목표를 보존합니다.
2. 밀던 목표를 취소한 뒤 해당 팔에는 리더 추종 목표를 반복 전송하지 않습니다.
3. 다른 팔은 계속 추종하고, 대기 중인 팔의 리더 위치도 계속 읽습니다.
4. 대기 중 이동하지 못한 목표를 누적하지 않습니다.

명령 없는 자동 재개:

- **반대로 되돌리기:** 대기 직전에 밀고 있던 관절들의 방향을 기록합니다. 해당 관절의 리더 목표가 팔로워 정지 위치보다 반대쪽으로 2° 이상 넘어간 상태를 0.2초 유지하면 재개합니다. 여러 관절이 밀고 있었다면 모두 조건을 만족해야 합니다. 나머지 관절까지 정지 자세에 정확히 맞출 필요는 없습니다.
- **같은 자세로 맞추기:** 전체 관절 목표와 실제 위치 차이가 3° 이내인 상태를 0.5초 유지하면 재개합니다.
- 두 경우 모두 대기 이후 리더가 2° 넘게 움직였다는 조건이 필요합니다. 대기시켜 오차가 줄었다는 이유만으로 같은 막힌 목표를 다시 시도하지 않습니다.
- 재개 시 빠른 추종 속도를 사용하며, 다시 막히면 해당 팔이 다시 대기합니다.

리더 목표를 계속 장애물 쪽에 둔 채 장애물만 치우면 코드가 제거 사실을 알 수 없습니다. 이 경우 사용자가 경로를 확인한 뒤 `--resume A/B/both`로 수동 재개합니다. 이 요청은 선택한 대기 팔만 천천히 재정렬하고 다른 팔의 속도는 바꾸지 않습니다.

대기 상태에서 일반 실행 명령을 다시 내리면 현재 대기 팔을 보존합니다. 서비스 종료·전원 재시작을 넘어 장애물 정보가 영구 보존되는 기능은 구현하지 않았습니다.

## 7. 유지한 한계와 고장 처리

- 11번: 논리 548~1572, 기준 좌우 45°.
- 13번: 모터 EEPROM 위치 범위 1024~3140. 대응 리더가 범위를 넘으면 경계에서 유지하고 돌아오면 따라갑니다.
- 21번: 논리 1~4095. 그 외 위치 제어 모터는 읽어 확인한 모터 범위를 사용합니다.
- 범위 밖의 목표만으로 전체를 정지하지는 않습니다. 기구 전체의 충돌 없는 가동 범위를 검증한 것은 아니어서 팔 관절의 `reviewed=false`를 유지합니다.
- 통신 실패, 오래된 응답, 제어 주기 초과, 큰 위치 불연속, 토크 상태 변화, 모터 하드웨어 오류, 60°C 이상 과열 등은 복구 가능한 장애물 대기와 구분하여 전체 추종을 정지시킵니다.
- 팔로워 Bus Watchdog은 15(300 ms)로 유지합니다. 오류가 발생하면 가능한 범위에서 자세 유지를 시도하며, 전원/통신 고장 중 자세 유지 성공을 보장할 수는 없습니다.
- 코드 종료는 일반적으로 토크 OFF를 수행하지 않습니다. 하중을 받는 팔을 받치지 않고 전원이나 토크를 끄면 처질 수 있습니다.

`config/robot.json`의 범용 `safety.max_speed_deg_s=15`와 현재 직접 추종용 `direct_A/B.follow_speed_deg_s=180`을 혼동하지 않습니다. 현재 실행 경로는 후자를 사용합니다.

모터 P/I/D와 전압·온도·토크의 작성 시점 실제 읽기 값은 체크포인트의 `status.json`에 보관합니다. 게인 자동 복원은 모든 모터를 일괄 덮어쓰는 기능이 아닙니다. 현재 12번의 확인된 P Gain 복원 경로가 있으며, 다른 RAM 설정은 전원 재시작 뒤 확인이 필요할 수 있습니다.

## 10. 검증 상태와 남은 작업

사용자는 A/B 모두 리더를 따라 움직이고 원래 자세로 돌아오는 것을 확인했습니다. 장애물에서 반대로 되돌릴 때 자동 재개되는 것도 사용자 확인을 받았습니다. 그 자동 재개의 속도를 개선한 최종 코드는 실시간 A/B 서비스에 적용했고 양쪽 `following` 상태를 확인했습니다. 최종 속도 변경 후 별도 지연 계측이나 반복 충돌 실험은 수행하지 않았습니다.

코드 검증: `.venv/bin/python -m pytest -q`, **164개 통과**. 마지막 코드 변경 뒤 실행한 결과입니다. 자동 재개 속도·첫 명령 변화량 제한·느린 초기 정렬 및 수동 재개 유지·장애물 쪽 목표 자동 재시도 방지·팔별 대기·하드웨어 오류 처리를 포함합니다. 이 테스트는 모의 장치 검증이며 전체 기구의 충돌 안전성을 인증하지 않습니다.

남은 작업은 B 그리퍼 수리와 열린/닫힌 위치 보정, 기구의 실제 관절 한계 정리, 전체 범위 자세 정밀도 및 지연 측정, 재부팅 후 새 서비스 경로의 실물 재확인, Isaac Sim 연결입니다. 이번 문서 정리 중에는 구동 설정을 변경하거나 재시작하지 않았습니다.

## 11. 보관용 체크포인트

`docs/checkpoints/2026-09-13/`에 코드와 문서 ZIP, 설정 사본, 작성 시점 상태 사본, 파일 해시 목록을 보관합니다. ZIP은 Python 코드·설정·테스트·문서를 포함하고 `.venv`, 대용량 연속 로그, 참조 저장소, 보드 펌웨어는 포함하지 않습니다. 과거 측정 로그 원본은 기존 `work/`에 남아 있습니다. ZIP을 실행 중인 폴더에 바로 풀어 덮어쓰는 방식으로 복원하지 않습니다.

의존성은 Python 3.10 이상, `dynamixel-sdk==4.0.5`, `pyserial==3.5`; 개발 테스트는 pytest 8 이상 10 미만입니다. 현재 `.venv`가 준비되어 있으므로 평소 실행에는 재설치가 필요하지 않습니다.

참고한 ROBOTIS 저장소의 로컬 사본은 `work/reference/open_manipulator`입니다. 최신 관절 목표 발행과 관절별 제한 처리 개념을 참고했으며 ROS 키보드 텔레오퍼레이션을 그대로 실행하는 구조는 아닙니다. 현재 구현은 실제 리더 엔코더를 읽어 DYNAMIXEL 모터에 직접 대응합니다.

## 12. 당일 종료 기록 — 토크 OFF 및 서비스 종료

사용자의 명시적 토크 OFF 요청으로 추종이 정지된 상태에서 11~15·21~24번 Torque Enable(64)=0을 쓰고 Bus Watchdog(98)=0으로 해제했습니다. 기존에 꺼져 있던 리더를 포함해 활성 18개 모터의 토크가 모두 0인 것을 읽기로 확인했습니다. 제외된 25·30번에는 읽기/쓰기를 수행하지 않았습니다.

기존 USB 연결을 사용하는 `teleop/live_actions.py`에 명시적인 `torque_off` 작업을 추가했습니다. 한 모터 쓰기에 실패하더라도 나머지 대상 모터의 해제를 시도하고, 마지막 읽기에서 토크가 남거나 쓰기 오류가 있으면 실패로 보고합니다. 일반 `--hold`와 Ctrl+C는 계속 토크 유지이며 이 작업과 다릅니다. `run_teleop.py --status`에 토크 OFF 표시도 추가했습니다. 별도의 사용자 CLI 토크 OFF 옵션을 추가한 것은 아닙니다.

사용자의 당일 작업 종료 요청 후 최신 서비스 측정에서도 활성 18개 모두 토크 0임을 다시 확인한 뒤, `shutdown` 요청 nonce 23으로 기존 서비스 PID 28807을 정상 종료했습니다. 시리얼 연결과 연속 로그 기록을 종료하고 서비스에 붙어 있던 절전 억제도 해제했습니다. 모터 전원 자체를 소프트웨어로 차단한 것은 아닙니다.

종료 근거 파일:

- `work/torque_off_confirmed.json`: 토크 해제 직후 읽기 결과.
- `work/end_of_day_motor_state.json`: 서비스 종료 직전 최신 측정값.
- `work/active_hardware_session.json`: `status=stopped`, `service_running=false`, `torque_off_verified=true`.
- `work/teleop_status.json`: 서비스 종료 표시와 마지막 모터 측정값. 종료 이후의 실시간 측정값이 아닙니다.

최종 코드 검증에는 토크 OFF의 활성 ID 제한, 일부 쓰기 실패 시 나머지 해제 시도 및 오류 보고 검증을 추가했습니다. 최종 검사 결과는 `docs/checkpoints/2026-09-13-final/validation.txt`에 저장합니다. 이 최종 백업은 토크 해제 처리까지 포함하며 기존 `2026-09-13/` 추종 시점 백업을 덮어쓰지 않았습니다. 대용량 로그와 중간 시험 파일도 삭제하지 않았습니다.
